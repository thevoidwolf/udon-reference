# Type Identity

Udon's VM does not implement C#'s normal runtime type system across `UdonSharpBehaviour` user types — there is no fast `behaviour is MyScript` check and no `(MyScript)behaviour` cast that works generally at runtime. To work around this, `UdonSharpBehaviour` exposes a deterministic numeric **type ID** and a string **type name**, both computed at compile time from the class's full type name.

Source: `Runtime/UdonSharpBehaviour.cs` and `Runtime/UdonSharpRuntimeUtils.cs`. **[Source]**

---

## `GetUdonTypeID`

```csharp
public long GetUdonTypeID()
public static long GetUdonTypeID<T>() where T : UdonSharpBehaviour
```

Returns a stable 64-bit hash of the class's full (namespace-qualified) type name. The hash is `SHA-256(typeName)` truncated to the first 8 bytes (`BitConverter.ToInt64`). The compiler bakes the ID into each program as the hidden variable `__refl_typeid` (and, for classes in an inheritance chain, the array `__refl_typeids` holding the IDs of the class and every U# base class). **[Source]**

- Returns `0` for behaviours whose program is a graph program rather than U#.
- Two clients running the same world will compute the same ID for the same class.
- Renaming or moving a class to a different namespace **changes its ID**.

**Use case:** check what user type an `UdonBehaviour` (or `UdonSharpBehaviour`) reference actually is at runtime.

```csharp
public UdonBehaviour someBehaviour;

void Start() {
    object raw = someBehaviour.GetProgramVariable("__refl_typeid"); // generated by compiler; null on graph programs
    long id = raw == null ? 0 : (long)raw;
    if (id == UdonSharpBehaviour.GetUdonTypeID<MyScript>()) {
        // handle MyScript case
    }
}
```

In practice U# does this comparison for you: `GetComponent<T>()`, `GetComponentInChildren<T>()` etc. with a U# type `T` are compiled to a shim that compares each `UdonBehaviour`'s `__refl_typeid` against `GetUdonTypeID<T>()` (`Runtime/Libraries/CompilerInternal/GetComponentShim.cs`). **[Source]** You usually only call `GetUdonTypeID` explicitly when handing references around as plain `UdonBehaviour`s.

## `GetUdonTypeName`

```csharp
public string GetUdonTypeName()
public static string GetUdonTypeName<T>() where T : UdonSharpBehaviour
```

What you get depends on where the code runs: **[Source]**

- **In compiled Udon (in-game, ClientSim):** the compiler-baked `__refl_typename`, i.e. the **namespace-qualified** name (`MyGame.Greeter`). The generic `GetUdonTypeName<T>()` is folded to the same string constant at compile time.
- **In plain C# on the editor proxy** (editor scripts, the stub in `UdonSharpBehaviour.cs`): `type.Name`, the **unqualified** name (`Greeter`).

Because of that mismatch, prefer `GetUdonTypeID` for equality checks and only use the name for debug logging.

```csharp
Debug.Log($"This is a {GetUdonTypeName()}");   // in-game: "This is a MyGame.Greeter"
```

## Implementation note

The hash is computed by `UdonSharp.Internal.UdonSharpInternalUtility.GetTypeID`:

```csharp
public static long GetTypeID(System.Type type)
{
    SHA256 typeHash = new SHA256CryptoServiceProvider();
    byte[] hash = typeHash.ComputeHash(Encoding.UTF8.GetBytes(type.FullName));
    return BitConverter.ToInt64(hash, 0);
}
```

Source: `Runtime/UdonSharpRuntimeUtils.cs`. **[Source]** The compiler computes the baked ID from the Roslyn display name (`NameAndContainingTypesAndNamespaces`), which for a **nested** class uses `Outer.Inner` whereas `Type.FullName` uses `Outer+Inner` — so editor-side and in-game IDs can differ for nested U# classes. **[Source]** (`Editor/Compiler/UdonSharpCompilerV1.cs`, `TypeSymbol.GetFullTypeName`)

The first 8 bytes of an SHA-256 give 64 bits of entropy — collisions across two U# class names in a realistic project are vanishingly unlikely. The hash is not cryptographically meaningful here; SHA-256 was chosen as a stable, available, deterministic hash, not a security primitive.
